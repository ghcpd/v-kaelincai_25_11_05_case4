- Flaky behavior reproduced: simultaneous asynchronous scoring requests cause read-modify-write races leading to lost updates; unreliable retries may also cause duplicates or overwrites; responses may arrive out-of-order resulting in different total scores for the exact same input.

## Root Cause & Fix Summary (technical) 🧭

- Root cause:
  - Read-modify-write race in aggregator tasks updating shared 'score' without synchronization.
  - Naive retries cause duplicates or overwrites.
  - Returning early (not waiting for all asynchronous calls) exposes partial states.

- Fixes in Project_B_Deterministic:
  - All scorer calls are awaited using asyncio.gather.
  - Results collected and sorted deterministically (ordered aggregation).
  - Atomic aggregation step (sum after gather).
  - Simple idempotency: in-memory processed_submissions store ensures repeated submission IDs produce the same result (prevents duplicates).
  - Bounded retry with exponential backoff implemented for scorer calls.

## Limitations & Notes ⚠️
- Mocked scorer: tests use lightweight mock services that accept per-request config. This is adequate to reproduce flakiness and verify deterministic behavior, but not a full production system.
- Persistent idempotency / transactional commit logic would be required for real multi-node production-grade deployments (use Redis, databases, or message brokers with once semantics).
- Tests use subprocesses and in-memory storage; concurrency behavior is reproducible under the configured delays but actual race manifestations depend on system scheduling.
- For higher-fidelity testing of distributed issues, consider spinning up Docker containers or an integration test environment simulating network partitions.
